## 7. 阶段一：拆开关键词与字符相似度

### 7.1 阅读现有公式

```text
HybridIndex 当前：
score = 0.7 × token_count_cosine + 0.3 × char_count_cosine
```

先让实验脚本分别输出这两项，再与原加权结果对照。说明：

- 英文、数字、下划线主要由正则抽取，中文采用相邻字符片段，不能等同于完整中文分词。
- 字符分支按字符计数，可能因常见汉字、标点等获得相似度。
- 关键词频次余弦没有 BM25 的 IDF、文档长度处理机制，不要给当前实现贴 BM25 标签。

### 7.2 建立独立 KeywordIndex

建议提取一个使用 tokenize() + Counter + _cosine() 的 KeywordIndex；也可增加等价的独立函数，但不能把原 HybridIndex 的混合分数直接命名为纯关键词分数。

最小接口：add(sources)、search(query, top_k=5, *, allowed_ids=None)。保持 Source 输出，score 使用词项余弦。

约定：

- 空白问题返回 []；非法 top_k 拒绝，bool 不作为合法整数。
- 无词项交集返回空结果，不为了凑足数量塞入零分文本。
- 同分按 source_id 排序，以便复现。
- 使用同一份 Source 内容与 ID，不给另一分支重新编号。
- 原始 Source 不被修改；返回副本，嵌套 metadata 需要独立复制。

用“offset”“max_steps”“model_name”等精确术语和一条同义改写问题做实验，记录关键词分支优势与漏检。特殊符号、大小写、中文边界都先看 tokenize 实际输出再解释。

检查点：分别展示纯关键词、纯字符、原混合频次三列结果，能说明它们共享与不同的表示方式。

## 8. 阶段二：建立两路共同检索契约

主线采用 **KeywordIndex + ChromaIndex**。两路读取同一份规范 Source 清单。

建议初始参数：每路 candidate_k=6，最终 top_k=3。必须解释：

| 参数 | 控制什么 |
|---|---|
| candidate_k | 每个分支最多提供多少候选给融合 |
| top_k | 融合之后最多保留多少片段 |
| context budget | 这些片段真正进入上下文时占用多少容量 |

candidate_k 至少不小于 top_k；限制在当前可用记录数内。更大的候选集合可能改善覆盖，也可能增加耗时和干扰，不能无限扩大。

今天可以串行运行两路，并分别计时。关键词评分和本地 Embedding 是同步工作，直接包 async 不会自动获得并发收益。

推荐额外返回一份诊断信息：分支状态、耗时、候选数、过滤后数量、最终数量、降级原因。Source 列表继续用于传递证据。

在轨迹里保留：分支名、原始 score、metric、rank、融合贡献。Chroma 返回的 `_retrieval` 是运行时字段，不能拿查询后的 Source 再原样写回当前 ChromaIndex，因为现有写入契约禁止该保留字段。需要重建库时使用加载器提供的规范 Source。

## 9. 阶段三：分数归一化与 RRF

### 9.1 先理解不能直接加分

词项余弦、向量余弦与未来 BM25 的分数含义和分布不同。即使两路都在 0～1 内，也不能说明 0.8 表达相同程度的相关性。

做 min-max 对照：对每路已检索候选单独计算

```text
normalized(s) = (s - min_score) / (max_score - min_score)
combined = 0.5 × keyword_normalized + 0.5 × vector_normalized
```

实验约定：缺席某路贡献 0；同一路全部同分时，已出现候选统一赋 1，并明确这只是教学选择，不存在普遍正确的默认值。也试一次全部赋 0，观察排名如何变化。

必须测试空列表、单个候选、全部同分、向量负分。距离先转换为越大越好的 score，再归一化。

解释两个限制：改变 candidate_k 会改变极值，从而改变归一化分数；只剩一个很差候选时也可能被赋为 1。归一化统一了尺度，不等于校准了证据可信度。

### 9.2 主线使用 RRF

RRF 根据各分支的排名累加贡献，无需把原始分数强行解释成同一种尺度。排名从 1 开始，未出现在该分支的贡献为 0。[RRF 官方实现说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

```text
rrf_score(source) = Σ 1 / (rank_constant + rank_in_branch)
```

沿用项目 rank_constant=60；它与最终 top_k 无关。

手算样例：关键词 [A,B,C]，向量 [B,D,A]。

| 来源 | 关键词贡献 | 向量贡献 | 总分约值 |
|---|---:|---:|---:|
| A | 1/61 | 1/63 | 0.03227 |
| B | 1/62 | 1/61 | 0.03252 |
| C | 1/63 | 0 | 0.01587 |
| D | 0 | 1/62 | 0.01613 |

预期排序 B、A、D、C。分别解释“某路第一”与“两路都靠前”如何影响总分。RRF 分数只是排序量，不能转成答案正确概率。

### 9.3 修正 merge_ranked 的边界

阅读当前实现后补充：

1. top_k 与 rank_constant 的合法性；空分支与所有分支为空。
2. **同一路先按 ID 去重再重新连续排名**，重复 ID 只能贡献一次。
3. 跨路相同 ID 累加贡献，最终只输出一个 Source。
4. 并列按 source_id 排序。
5. 相同 ID 但正文或来源字段冲突时明确报错，不能由“最后一个列表”悄悄覆盖。
6. 输出副本并保留两路轨迹，不修改输入列表或规范 Source。

Source 冲突判断不比较检索 score、rank 等运行时字段；比较 content、file_path、page、url 和关键来源 metadata。最好按 source_id 从统一来源清单取规范对象，再附加本次检索轨迹。

检查点：把关键词列表改为 [A,A,B,C]，按今天去重约定结果应与 [A,B,C] 相同。能在测试里证明，不只口头承诺。

## 10. 阶段四：来源过滤必须在正确的位置执行

### 10.1 先定义过滤含义

核心支持本地 file_type（txt/markdown/pdf）和用户指定文件集合。网页 domain 过滤可使用固定网页 Source 做扩展，不需要今天访问真实网络。

建议用统一 allowed_ids 集合传给两路：None=不限制；空集合=明确没有允许来源，必须返回 []，不能把空集合误当作不限制。

多个限制共同出现时按 AND 取交集。未知过滤字段应明确拒绝，不能忽略后返回更大范围。

### 10.2 为什么不能先取 Top-3 再过滤

构造例子：全库前 3 条都是 TXT，只有第 4 条是相关 PDF。用户只选 PDF。

- 先取 3 条再筛 PDF：得到空列表。
- 先限制 PDF 再选最近 3 条：可以找到该 PDF。

因此两路都要在候选截断前使用相同范围。

### 10.3 当前项目的可行实现

小语料可先从规范 Source 清单生成 allowed_ids：关键词分支只给允许对象评分；Chroma 查询按可过滤的 source_id 字段限制。

当前 Chroma metadata 没有这个顶层字段，需在新实验集合写入时增加如 `filter_source_id`、`filter_file_type`、`filter_relative_path`，并从规范字段计算，不能由任意检索轨迹覆盖。保留原 source_metadata_json 用于完整还原。

示例 where 参数：

```python
where = {"filter_source_id": {"$in": sorted(allowed_ids)}}
```

这是非空允许集合的示意，先处理空集合再发请求。过滤后的有效数量可能小于全库 count，使用过滤范围内数量确定 n_results。可以用 collection.get(where=..., include=["metadatas"]) 的 IDs 计数；对于今天的小语料代价可接受。

Chroma 支持通过 where 对 metadata 加条件；可结合 $and、$in 等操作符。采用前核对安装版本与文档。[Chroma metadata filtering](https://docs.trychroma.com/docs/querying-collections/metadata-filtering)

使用独立 Day 09 新集合回填这些字段；不直接改旧 Day 08 库并假定历史记录已更新。若暂时采用取全库候选后过滤的小数据替代方案，应注明规模限制，且必须在截取分支候选数之前完成过滤。

检查点：只选 PDF 时，两路、融合结果和最终上下文均无 TXT；选不存在文件时结果为空；诊断能看到允许来源数。

## 11. 阶段五：去重时保留证据出处

区分三类问题：

| 场景 | 今日策略 |
|---|---|
| 同一路重复 source_id | 去重后计排名，不重复加分 |
| 两路同一个 source_id | 合并为一个，累加两路贡献 |
| 不同 ID 但正文相同或部分重叠 | 保留来源差异；扩展阶段再做内容合并 |

不能直接按 file_path 去重，否则同一 PDF 不同页的互补证据会丢失。也不能只按正文 hash 删除其他来源，除非同步保留所有出处。

核心实现只做精确 ID 去重。记录重复正文与相邻重叠片段数；如要做内容去重，需附带 alternate_sources，不修改现有 offset，不把合并文本假装成原始片段。

检查点：同文件不同页可同时保留；一个 ID 的多路命中能解释；规范 Source 在融合前后保持一致。

## 12. 阶段六：把候选变成受预算约束的上下文

### 12.1 今天采用可验证的字符预算

先实现 max_context_chars=2000 的教学预算，明确单位为 Python 字符数，不将其称为模型 token 上限。DeepSeek 的实际输入长度还包含系统提示、用户问题、其他消息和输出预留，Day 10 接入时需要单独计算。

不能用 BGE tokenizer 的计数当作 DeepSeek 的精确 token 数。若后续有匹配目标模型的 tokenizer，可将预算计数器替换为该实现。

### 12.2 输出结构

建议 build_context 返回：text、included_source_ids、omitted_source_ids、used_chars、budget、omission_reasons。证据块格式示意：

```text
[source_id: doc-实际ID]
文件：guide.pdf；物理页：2；位置：120–380
正文：这里是 Source.content 的完整片段。
```

来源标题、分隔符、换行也计入预算。若上下文总外壳额外包含说明，必须一起计数。

主线采用“按融合排名依次尝试，整块放入；放不下则跳过，继续尝试后续更短块”。不截掉半句，不改 Source.content 或 offset。所有块都放不下时返回明确的 budget_exhausted 诊断。

该策略可能跳过最相关的长片段，所以必须保存遗漏原因；今天不要将它宣称为最优装包算法。

### 12.3 必做实验

构造三段长度不同且证据不同的片段，预算从足够大逐步减少，观察 included_source_ids 与正文。验证：

- len(text) 不超过预算。
- 每个块都能从 source_id 回到原文件/页码。
- 未进入上下文的来源不被列为“已使用证据”。
- 显示文本不会改变原文坐标。
- 单条过长、空输入、非法预算都有明确行为。

检索文档中的指令性内容仍然是待分析资料，不是用户授权。上下文边界应标记清楚；不能把检索正文拼成新的 system 指令。

## 13. 阶段七：失败和降级契约

今天定义最小结果状态，不引入复杂调度：

| 情况 | 行为 |
|---|---|
| 两路正常 | 融合并标记正常 |
| 一路正常但无结果 | 合并另一条结果，记录该路空结果 |
| 向量模型或库发生预期运行错误 | 在显式允许降级时使用关键词，标记 degraded 并保留原因 |
| 关键词分支发生预期错误 | 同理可使用向量分支 |
| 两路都失败 | 明确整体失败，不显示为“未找到资料” |
| 来源过滤非法或同 ID 内容冲突 | 拒绝处理，不通过降级绕过一致性问题 |

只捕获明确可降级的运行错误，不用 except Exception 把程序缺陷全部吞掉。降级结果进入单独统计，不能作为完整双路实验参与公平对照。

诊断记录问题 ID、分支名、候选数量、耗时与错误类型。合成资料可保留完整候选用于学习；真实敏感文档以后需要更严格的日志范围。

## 14. 阶段八：做公平的三组对比

### 14.1 主表

在同一次运行、同一份数据上比较：

1. KeywordIndex 独立结果。
2. ChromaIndex 真实向量结果。
3. KeywordIndex + ChromaIndex 的 RRF 融合结果。

每路先获取相同 candidate_k=6；独立方法截取 Top-3，融合对两份候选排序后截取 Top-3。记录 candidate_k，避免不同窗口的结果被误认为相同配置。

min-max 与字符相似度是附加解释性结果，不替代这三组主表。

### 14.2 保留原基线，再加挑战组

原 Day 08 10 题 + 2 个探针完整保留。已有 Hit@3=10/10，今天重点观察是否退化、Top-1 是否改变和新引入多少不支持的候选。

可增加 4～6 条挑战问题，先固定答案依据，再运行：

- 精确术语：询问 source_id、max_steps 或语料中真实存在的错误码。
- 同义改写：使用不同表达询问已有概念。
- 相近主题干扰：两个片段词汇接近但只有一个直接支持。
- 来源约束：同一问题只允许 PDF 或指定文件。
- 无允许证据：限制到不含答案的文件，结果应记录缺证据。

新增资料或题目另存版本；报告原基线组与挑战组各自的分母，不能把过滤后不存在答案的问题混入正向 Hit@3 分母。

### 14.3 审核与指标

沿用 Day 08 等级：0=无关/不支持，1=主题相关但缺关键证据，2=正文直接支持。每个候选保留理由；如由 AI 辅助审核，明确记录，并由你抽查关键成功与失败例子。

| 指标 | 定义与用途 |
|---|---|
| Hit@3 | 正向题 Top-3 至少一个等级 2 的比例 |
| Top-1 支持率 | 正向题首条为等级 2 的比例 |
| 上下文保留命中率 | 正向题经过预算后仍保留至少一条直接支持证据的比例 |
| 候选重复率 | 记录计算阶段与分母，观察重复带来的容量浪费 |
| 过滤违规数 | 返回不在允许集合的 ID 数，必须为 0 |
| 耗时与上下文字符数 | 冷启动与热查询分开，比较成本 |

候选重复率建议按“融合前各路原始候选总数减去唯一 ID 数，再除总数”计算；总数为 0 时记为 0。跨路重合本来就是有用信号，不应把这个指标越低视为越好。

报告模板：

| 问题 | 关键词 Top-3 | 向量 Top-3 | RRF Top-3 | 三路 Hit | 预算后证据 | 解释 |
|---|---|---|---|---|---|---|
| Q01 | 实际 ID | 实际 ID | 实际 ID | 实际审核 | 实际 ID | 提升/持平/退化原因 |

至少分析一个关键词有优势的例子、一个向量有优势的例子，以及一个融合持平或退化的例子。若真实数据没有出现某类差异，明确写“本数据未观察到”，再用独立合成案例解释机制，不能伪造实验结果。

## 17. 常见问题与排查方向

| 现象 | 优先检查 |
|---|---|
| RRF 总分异常高 | 同一路重复 ID 是否重复计分 |
| 语义匹配不错但融合下降 | 另一分支是否加入主题干扰；候选窗口与排名贡献 |
| 过滤 PDF 后空结果 | 是否先截断；旧集合是否缺可过滤字段 |
| 过滤条件为空却返回全库 | None 与空集合是否被混用 |
| 数据看似相同但标签匹配失败 | 是否移动文件或改切片，导致 source_id 变化 |
| 元数据互相污染 | model_copy 默认浅复制，嵌套字典是否共享 |
| 写回索引时报 _retrieval 错误 | 是否误将查询对象当作规范索引输入 |
| Hit@3 好但回答缺证据 | 预算装包是否丢弃了支持片段 |
| 混合实验看似更快 | 是否只给其中一路计算了模型冷启动 |
| 融合没有超过 Day 08 | 基线已达 10/10，查看 Top-1、挑战组与退化而非强求提升 |
