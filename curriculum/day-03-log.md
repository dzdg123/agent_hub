## 我能独立解释的概念

以下为结合代码整理的复习笔记，独立口头验收待自己确认：

| 概念 | 结合实验的解释 |
|---|---|
| 协程函数 | async def 定义的函数；加 async 不会自动让内部阻塞代码变成异步 |
| 协程对象 | 调用协程函数得到待执行对象，需 await 或调度 |
| await | 等待结果；实际挂起时，事件循环可推进其他任务 |
| Task | 交给事件循环调度的协程，不等于线程 |
| 事件循环 | 协调任务执行、等待和恢复；本实验的 Python 代码在单线程推进 |
| 串行与并发 | 循环里逐个 await 是串行；gather 安排多个协程，让等待重叠 |
| 并发与并行 | 并发是多个任务交替推进；并行是同一时刻实际执行多项工作 |
| gather | await 后获得结果列表，结果顺序按输入顺序，不按完成顺序 |
| Semaphore | 限制同时占用名额的数量，不等于每秒请求次数限制 |
| active 与 peak_active | 当前已取得名额的请求数，以及本批次达到的最大值 |
| finally 与 async with | 前者确保计数更新；后者负责退出时释放 Semaphore 名额 |

### 超时范围的选择

本实验后续采用“取得 Semaphore 名额后才开始计算超时”，排队等待不占用请求超时预算。像排队买奶茶：轮到我以后才要求在规定时间内做好。

若把 wait_for 包在整个“排队＋请求”协程外面，则从排队开始计时，可能还没获得名额就超时。比如排队 0.2 秒、请求 0.1 秒、预算 0.25 秒：只算请求可成功，合计计算则超时。

当前 `timed_request()` 直接调用模拟请求，还没有和 Semaphore 组合；上面记录的是已选择的设计，不是组合实验的实测结果。

### 与真实 Agent 代码的对应

`llm.py` 的 `await client.post(...)` 对应网络等待，`await asyncio.sleep(...)` 对应重试退避等待。多个独立网页请求可以并发；`mini_agent.py` 必须先等待模型生成工具调用，再执行工具，再把结果放回消息列表，供下一轮模型使用。这些步骤存在数据依赖，不能任意同时执行。

默认 gather 遇到普通异常时向调用方传播异常，本身不会因此自动取消其他任务；若异常使 main 退出，asyncio.run 关闭事件循环时会取消剩余任务。这两个行为要分开理解，当前尚未运行专门的对照实验。

## 阶段七：阻塞事件循环对照实验

条件：3 个请求，每个等待 0.2 秒，均使用 gather 调度。

- asyncio.sleep 组实测：0.2 秒
- time.sleep 组实测：0.6 秒
- 异步组的开始/结束顺序：ABC 同时执行
- 阻塞组的开始/结束顺序：A B C 按顺序执行

解释：
asyncio.sleep 会挂起当前任务，让其他任务推进。
time.sleep 会阻塞事件循环所在的线程。
async def 和 gather 不会自动消除函数内部的阻塞。
